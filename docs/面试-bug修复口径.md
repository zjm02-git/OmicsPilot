# 面试口径：四个「结论级 bug」

> 这份文档里所有数字都来自**修复后重跑的真实输出**，不是凭记忆。
> 数据：TCGA-BRCA 重新拉取（60 tumor vs 60 normal，19938 基因 × 120 样本，缺失 0 格）。
> 每个 bug 都能证明一件事：**我懂这套系统在算什么**——比"我搭了个 Agent"值钱。

---

## Bug 1｜log2FC 对已经是 log2 的数据又取了一次 log2（双重取对数）

**现象**
同一个问题"哪些基因差异表达"，旧代码判出 **2597 个**显著基因，正确口径只有 **1587 个**；
而且两者只有 **688 个**基因重合 —— 也就是说**旧口径里有 1909 个基因是凭空冒出来的**，
同时还漏掉了 899 个真阳性。

**根因**
上游 `fetch_tcga.py` 写出的表达量已经是对数刻度：`log2(fpkm_uq + 1)`。
`diff.py` 却对两组均值再算一次 `log2(mean_b / mean_a)` —— 这是**对对数再取对数**，
得到的数没有"倍数"含义，而且依赖 +1 伪计数的平移量：换个伪计数，同一个基因的数值就变了。

修复：在 log2 刻度上直接相减 `log2FC = mean_b - mean_a`；只有线性刻度才用 `log2(比值)`。
代码里用 `input_scale="log2" | "linear"` 把「值空间契约」显式化。

**为什么之前一直没被发现**
1. 错出来的数落在 1~3 之间，肉眼看完全像 log2FC，"2.71 倍上调"读起来毫无破绽；
2. 单元测试的 fixture 用的是**线性**量纲（100 → 300），两种公式在那种数据上**恰好等价**，
   所以测试永远是绿的；
3. 覆盖率分母里根本没有 `diff.py` —— 88.6% 覆盖的是服务层七个文件。

**修复前后（同一份数据）**

| | 旧口径 | 新口径 |
|---|---|---|
| 显著基因数 | 2597 | **1587** |
| 两者交集 | 688 | |
| 只在旧口径出现 | 1909 | |
| 两种 log2FC 的 Pearson r（共同可检验的 15284 个基因） | 0.675 | |

补充：在全量 226 样本的旧数据上，同一组对比是 **3740 → 1579，r = 0.311**。

**30 秒讲法**
"我的数据已经是对数刻度了，我却又对均值之比取了一次 log2。这个 bug 不会报错，
只会让结果'看起来更显著'。我发现它是因为算出 2597 个显著基因，
但我用正确公式重算只有 1587 个，而且两者只重合 688 个 —— 选出来的根本不是同一批基因。"

## Bug 2｜富集分析里 BH 校正的 m 被 k==0 的通路提前裁掉

**现象**
富集结果的所有 FDR 系统性偏小 —— 也就是**比真实情况更容易宣称"显著富集"**。

**根因**
`enrichment.py` 的循环里有一句 `if K == 0 or k == 0: continue`，
写在 BH 多重检验校正**之前**。于是"在显著基因里一个都没命中的通路"被整个丢掉，
BH 的分母 m 变小，`p × m / rank` 变小，所有 FDR 一起变小。

**为什么之前没被发现**
偏小只会让结果更"好看"，不会报错，也不会有人怀疑 ——
一个只会往"发现"方向偏的 bug，天然缺少报错的动力。

**修复前后（同一份数据）**

| | 旧行为 | 新行为 |
|---|---|---|
| 参与 BH 的通路数 m（normal 更高的 1017 个基因） | 5458 | **7242** |
| m 被低估 | **24.6%** | — |
| 由此导致的 FDR 偏低 | 约 1.33 倍 | — |
| 显著通路数 | — | 916 |

修复同时加了基因集规模过滤 `5 ≤ K ≤ 500`：K 太小的注释是噪声，K 太大的泛类目
（细胞通讯、跨膜运输）几乎必然命中，会把 top 榜占满而没有信息量。

**30 秒讲法**
"BH 校正的分母是所有被检验过的通路。我之前在算 p 值之前就把'一个都没命中'的通路
`continue` 掉了，分母少了 24.6%，所以所有 FDR 都偏小 1.3 倍。
这类 bug 的危险在于它只会让结果更像'有发现'。"

## Bug 3｜113 个肿瘤样本只来自 112 个病人（aliquot 伪重复）

**现象**
同一份组织的不同等分瓶（01A / 01B）被当成了两个独立的生物学重复，
样本量虚高，p 值偏小。

**根因**
TCGA 的 barcode 是 `TCGA-A7-A0DC-01A`：前三段是病人，第四段是"组织 + 等分号"。
去重必须按**前三段**做；按整串做等于没去重。

**为什么之前没被发现**
样本数"正好"配平（113 vs 113），看起来比不配平更整齐 ——
正是这个"整齐"掩盖了重复。

**修复前后（真实下载输出）**

| 组 | 去重前 | 去重后 | 处理 |
|---|---|---|---|
| normal | 113 份等分 / 113 病人 | 113 / 113 | 无重复 |
| tumor | 120 份等分 / **119 病人** | **119 / 119** | 丢弃 1 份：`TCGA-A7-A0DC-01B` |

本次 60 vs 60 实际用了 **120 个样本 / 117 个病人**，其中 **3 个病人同时出现在两组**
（跨组的病人是真实设计问题，不是重复等分，已在报告里写明 n 的构成）。

同时修了一个更隐蔽的坑：旧代码取 `cases.samples[0]`，
一个病例若同时挂 01A（肿瘤）和 11A（正常）两份样本，可能把**肿瘤测序文件贴上正常 barcode**。

**30 秒讲法**
"TCGA 一个病人可能有两瓶等分。我按整串 barcode 去重等于没去重，
导致 113 个肿瘤样本其实只来自 112 个病人。伪重复会把 p 值算小，
而且它不会让样本数看起来异常 —— 反而更'整齐'。"

## Bug 4｜XACK 只清 PEL、不删条目，Stream 无限增长

**现象**
Redis Stream 的内存随任务数单调增长；`queue_len` 指标只增不减，用它做积压告警必然误报；
并且用户的原始请求文本（含在 message payload 里）**永久明文留存**。

**根因**
Redis Streams 的 `XACK` 只把消息从 PEL（待确认队列）里摘掉，
**条目本身仍留在 stream 里**，要 `XDEL` 或 `XTRIM` 才删。
旧代码只 ack，从不删。

**为什么之前没被发现**
功能上一切正常：任务照样跑、结果照样对。退化只发生在这三处——
内存、指标语义、数据留存合规。没有一条会报错。

**修复前后**

| | 修复前 | 修复后 |
|---|---|---|
| `grep xtrim\|xdel\|maxlen` | **0 命中** | — |
| 投递 | `XADD` 无上限 | `XADD maxlen=10000, approximate` |
| 确认 | 只 `XACK` | `XACK` + `XDEL`（ack / retry / dead_letter 三条路径都做） |
| `queue_len` 语义 | 历史任务总数（只增） | 真实积压（配合 `pending` 才是"执行中"） |

**30 秒讲法**
"Streams 的 XACK 只是确认，不是删除。我原来只 ack 不删，
Redis 内存会跟着任务数一直涨，而 queue_len 这个指标永远不会回落 ——
用它做告警，第一次就会误报。这类 bug 不会让功能出错，只会让系统在半年后 OOM。"

## 附：两条同源的正确性修复（顺带）

**缺失值不再静默补 0**
旧代码 `expr.get(g, {}).get(sid, 0.0)`：没测到也写 0，等于宣称"表达量为 0"，
于是 QC 的缺失率体检永远报 0.0%。
新的重取结果：**留空 0 / 2,392,560 个格子，真实缺失率 0.0000%**。
注意：矩阵里 13.11% 的 0 值是**源数据里真实的 fpkm_uq=0**（真零表达），不是补出来的 ——
这两件事以前是混在一起的，现在能分开了。

**取消 ≠ 质检未通过**
用户主动取消时，旧代码复用 `qc_passed=False`，报告标题渲染成"质检未通过"。
现在用独立字段 `review_decision` 区分，报告写"已由用户取消"；
并且取消产生的报告**不进缓存**（否则用户取消一次，24 小时内改不了主意）。

## 一句话总结（面试收尾用）

> 这四个 bug 有一个共同点：**它们都不会报错，只会让系统安静地算出错的东西**。
> 定位它们靠的不是"跑一下看看崩不崩"，而是想清楚每一步在算什么、
> 以及拿两个口径的真实数字去对撞 —— 2597 vs 1587、5458 vs 7242、112 vs 113。
