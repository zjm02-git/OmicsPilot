## 项目一：基于 LangGraph 的多组学数据分析智能体（GenPilot）

**技术栈**：Python · LangGraph（StateGraph / Checkpointer / interrupt）· LangChain · Chroma · FastAPI · SQLAlchemy · MySQL · PostgreSQL · Redis · Docker · Streamlit

**项目简介**：用户上传表达矩阵与分组表，用一句话描述需求，Agent 自动完成"数据识别 → 质检 → 人工确认 → 差异分析 → 通路富集 → 结果解读 → 出报告"，并把分析偏好写入长期记忆。

**主要工作**

- **上下文预算与降级**：对解读与问答的提示词做 token 预算化管理（6000 / 3000），按"差异结果 > 通路富集 > 基因功能注释"优先级整块裁剪，并在 prompt 中显式声明证据被裁减；模型不可用时降级输出统计摘要而非中断，**LLM 全挂场景端到端由 500 转为 200 并出完整报告**。
- **LLM 调用韧性**：因 OpenAI 兼容 SDK 无逐请求超时，用线程池在调用边界实现硬超时（意图 45s / 解读 120s），叠加指数退避 + 抖动重试与三态熔断；结构化输出解析失败时追加纠错消息重试，仍失败则退回关键词规则路由。**40% 失败率注入下，260 次任务成功率由 55.8% 提升至 90.4%**（调用数 260 → 416）。
- **缓存正确性与可用性**：缓存 key 由"问题文本"改为"归一化问题 + 数据集绝对路径 + 数据集指纹（文件名/大小/mtime 的 sha256）"，**修复了换数据集问同一句话会返回上一份报告的正确性缺陷**；Redis 为主 + 进程内 LRU 兜底、TTL ±10% 抖动防雪崩、`SET NX` single-flight 合并并发同问。**同问重复提交 0.49ms 命中（冷路径中位 25.72s），Redis 整体宕机时仍 200 返回（本地兜底 217.8ms）**。
- **降级产出隔离**：状态机新增 `degraded` 标记，模型抖动时生成的降级报告**不写入缓存**，避免一次故障污染 24 小时内所有同问请求；恢复后同问会真实重跑并回填正品（已用故障注入验证）。
- **长任务异步化**：新增 `/analyze_async` 与 `/jobs/{id}` 轮询，任务状态 `queued/running/done/error` 与阶段（质检/差异/富集/解读）可查，避免冷路径 20s+ 阻塞 HTTP 长连接。
- **可观测性与健康检查**：`X-Request-ID` 贯穿日志与响应，`/metrics` 暴露计数器与各路由 P50/P90/P95/P99，`/healthz` 按依赖分级（Redis 挂 → degraded 200，MySQL 挂 → down 503）；统一异常处理器返回可追踪的 `error_type` + `request_id`。
- **测试体系（单测 + 集成）**：**80 个 `unittest` 用例**（72 单测 + 8 Web 集成）覆盖缓存/韧性/上下文/指标/任务/HTTP 契约；集成测试用"真 TestClient + 真 Redis + 真 MySQL + 假模型"跑通 `/analyze → /confirm` 与 `/analyze_async → /jobs/{id}` 两条主链路（假模型仅在测试进程内替换 `get_model`，生产链路仍是真模型）；**9 个模块行覆盖率 74.8%**，`web.py` **67.5%**。自建压测实测**缓存命中路径 32 并发 / 512 请求 0 错误、77.0 req/s、P50 149ms / P95 268ms / P99 331ms**。
- **集成测试反哺出真 bug**：写集成测试时发现 `load_qc_node` 只校验分组列、不校验样本能否与表达矩阵对齐——用户上传缺少 `sample_id` 的分组表时质检照样通过，直到人工确认后才在差异分析里抛 `None of ['sample_id'] are in the columns`，被包装成"会话可能已失效"。已在质检阶段补样本对齐校验并加回归用例（`test_08`）。
- **真模型端到端**：真 DeepSeek + TCGA 真实数据（19938 基因 / tumor 113 vs normal 113）跑完整链路：`/analyze` **3.35s** → `/confirm` **23.72s**（总 **27.07s**），报告 **5502 字**、四章节齐全、`degraded=false`、跑完缓存可命中；脚本 `tools/e2e_live.py` 可复现。
- 数据侧：TCGA-BRCA 真实数据（19938 基因 × 226 样本，113 vs 113；独立病人 217，去重丢弃 3 份重复等分）；差异分析向量化（Welch t + BH 校正），富集分析走 GO 注释本地匹配；CSV 解析按 mtime+size 缓存，热读 0.38s → **0.0000s**。

**可被追问且答得出的点**

| 面试官可能问 | 你的答案依据 |
|---|---|
| 90.4% 怎么测的？ | `tools/bench.py::bench_retry_ab`，260 次任务、40% 概率注入 `ConnectionError`，统计最终是否产出报告；对照组 260 次调用，重试组 416 次（重试确实多花了调用） |
| 0.49ms 是不是假的？ | 缓存命中路径只做 key 计算 + 缓存 GET；冷路径 25.72s 是 3 次真 LLM 端到端的中位数（24.05 / 25.72 / 29.31） |
| 降级报告为什么不能缓存？ | 模型挂了只剩统计摘要，内容质量低于正品；若入缓存，24h 内所有同问请求都拿到残缺报告。用 `degraded` 标记 + `cache_skip_degraded_total` 计数验证 |
| single-flight 怎么实现？ | `SET lock:{key} NX EX 60`，抢到算，抢不到 `wait_for` 轮询结果；等待超时（180s）自己兜底重算，宁可重复不挂死 |
| 覆盖率 74.8%，剩下 25.2% 是什么？ | `web.py` 已到 67.5%，缺口主要是真模型分支与异常兜底（`unhandled_exception_handler`、任务 error 态等）；真实链路由 `tools/e2e_live.py` 单独验证。说清"哪块没测、为什么"比刷数字可信 |
| 集成测试里的假模型算不算造假？ | 不算。它只在测试进程内 `mock.patch("omics_agent.nodes.get_model")`，生产代码零改动；同一条链路另有 `tools/e2e_live.py` 用真模型跑通（27.07s / 5502 字 / 四章节齐全） |
| 为什么不用 Celery/RabbitMQ？ | 异步已经是 Redis Stream 真队列（消费组 / XAUTOCLAIM 超时接管 / 死信 / 幂等），跨进程、kill -9 不丢任务；环境装不了 Celery 而 Redis 现成，没必要为此再引入一套中间件。技能栏写"了解"，不写"使用" |

## 项目二：多工具 Agent（手写 ReAct，与固定流水线并存）

> **一句话定位**：在固定流水线之外手写 ReAct 多工具 Agent，让模型自主决定「下一步调哪个工具」，补上「固定图只能走死分支」的短板；难点是让调用**既自主又不失控**。
> 代码位置：`omics_agent/agent.py`（ReAct 图 + 9 个工具）、`omics_agent/mcp_client.py`（MCP 桥接 2 个工具）、`skills/`（两份 `SKILL.md`）、`mcp_servers/db_server.py`。

**技术栈**：Python · LangGraph（StateGraph / 条件边 / Checkpointer / Store）· LangChain（`@tool` / `bind_tools`）· MCP（stdio + JSON-RPC）· Agent Skills · NCBI E-utilities · 线程池硬超时

**主要工作（每条都能在源码里指到行）**

- **手写 ReAct 循环，不用 `create_react_agent`**：状态 / 模型 / `agent` 节点 / `tools` 节点 / 条件边 5 个零件手动搭「思考 → 选工具 → 执行 → 再思考」；`should_continue` 只看最后一条消息有没有 `tool_calls` 决定去 `tools` 还是 `END`。**为什么预算用尽时不能直接送 `END`**：那条带 `tool_calls` 的 `AIMessage` 若拿不到对应的 `ToolMessage`，历史不完整，下一次 `invoke` 会被 API 直接判 400——所以闸门放在 `agent_node` 入口，而不是路由函数里。
- **11 个 `@tool` 分四类**：5 个业务（`query_gene` / `run_differential` / `run_pca` / `run_clustering` / `search_literature`）+ 2 个 Skill（`list_skills` / `load_skill`）+ 2 个记忆（`recall_preferences` / `save_preference`）+ 2 个 MCP（`mcp_get_user_count` / `mcp_get_history`），`TOOLS = [5 业务, 2 Skill, 2 记忆, *MCP_TOOLS]`。入参 schema 由 `@tool` 函数的**类型注解**推断，运行时再用 `isinstance(args, dict)` 兜一道。
- **四道护栏（本项目真正的难点）**：
  1. **步数预算** `MAX_STEPS=8`：用尽后**换一个没 `bind_tools` 的 plain model**，从协议层把 `tool_calls` 能力拿掉，再注入 `LIMIT_NOTE` 让它基于已有结果作答——比在提示词里「求它别调工具」可靠得多，也不会抛 traceback。
  2. **指纹去重防原地打转**：指纹 = 工具名 + `json.dumps(args, sort_keys=True)`（参数顺序不同也判同一调用），同一指纹执行到第 2 次（`MAX_REPEAT=1`）直接拦截，回一条「已执行过 N 次，请基于已有信息作答或换参数」。
  3. **单工具超时** `TOOL_TIMEOUT=30` 秒：工具丢进 `ThreadPoolExecutor(max_workers=4)` 跑，超时只「不再等它」（Python 线程杀不掉，对方会自己跑完），避免一个联网检索卡死整个请求。
  4. **框架上限对齐**：自己算 `recursion_limit = MAX_STEPS*2 + 4`（一轮 ReAct = agent + tools 两个 super-step），避免出现「我们的护栏还没触发、LangGraph 先抛 `GraphRecursionError`」两套阈值打架。
- **失败一律变成可读文本交还模型**：工具不存在 / 参数不是对象 / 超时 / 内部异常，全部在 `_run_one_tool` 里转成一段 `ToolMessage` 文本（而不是抛 500 给用户），模型下一轮能自己换参数、换工具或干脆基于已有信息作答。**被拦截的重复调用也照样计步数**——否则模型一直重复同一调用时步数不涨、预算永远用不完，护栏形同虚设。
- **Agent Skills 渐进式披露**：`skills/differential`、`skills/enrichment` 各一份 `SKILL.md`；`list_skills` 只返回 name + description（**省 token 的关键**），`load_skill` 才把正文塞进上下文——按需加载，而不是把所有知识一次性灌进 system prompt。
- **接入 MCP 标准协议**：`mcp_servers/db_server.py` 把数据库只读查询（用户数 / 历史）包成独立 MCP server（stdio + JSON-RPC），Agent 侧用 `stdio_client` + `ClientSession` 桥接成普通 LangChain 工具；Agent 不直接 `import` 业务库，换库时 Agent 侧零改动。**踩过的两个坑**：早期每次调用都新起子进程重新握手（固定几百 ms），以及用 `asyncio.run()` 包同步调用——在 async 上下文里直接 `cannot be called from a running event loop`；现改为**常驻子进程 + 后台线程常驻事件循环**。
- **持久化与长期记忆**：Checkpointer 让同一 `thread_id` 多次 `invoke` 接着上次对话续跑（中断可恢复）；`Store` 存跨会话偏好（默认 `InMemoryStore`，`USE_POSTGRES=true` 换 `PostgresStore` 重启不丢），`save_preference` 写、`recall_preferences` 读。
- **文献检索走真实接口**：`search_literature` 直连 NCBI E-utilities（`esearch` 找 PMID → `efetch` 取摘要），不编造文献标题。

**可被追问且答得出的点**

| 面试官可能问 | 你的答案依据 |
|---|---|
| 为什么不用现成的 `create_react_agent` / `ToolNode`？ | 现成 `ToolNode` 不做三件事：指纹去重、单工具超时、步数计数。手写 `tools_node` 才能把这三件事塞进同一个节点（`_call_fingerprint` / `_TOOL_POOL` / `steps` 回写 state）。 |
| 模型一直重复调同一个工具怎么办？ | 指纹 = 工具名 + `json.dumps(sort_keys=True)`，第 2 次直接拦截、不执行，只回提示；且被拦的也算一步，预算照样消耗。 |
| 8 步用完了会怎样？ | 换 plain model + 注入 `LIMIT_NOTE`，模型只能基于已有工具结果作答；`guard_note` 一并带回给调用方。 |
| MCP 为什么要常驻子进程？ | 每次调用重建 stdio 进程 + 重新握手有几百 ms 固定开销；且 `asyncio.run()` 不能在已有事件循环里调用，所以要在后台线程跑一个常驻 loop。 |
| 11 个工具怎么当场证明？ | `agent.py` 里 9 个 `@tool` + `mcp_client.py` 里 2 个 = 11，`grep -c "@tool"` 当场能数；`TOOLS` 列表里 `*MCP_TOOLS` 展开接入。 |

**目前没做、外面别说过头的**

- 多轮超长对话的**历史裁剪**（`trim_messages` 之类）还没做：ReAct 侧靠 `MAX_STEPS=8` 限制轮数，但单条工具结果很长时没有 token 预算裁剪。
- 没有独立 Pydantic `args_schema`，也没用 `handle_tool_errors` 参数：**schema 由 `@tool` 函数注解推断，异常兜底写在 `_run_one_tool` 里**。被问到就照实说这两者，别说成"我手写了 args_schema"。

## 措辞对照（原句 → 改法）

| 原来 | 改成 | 为什么 |
|---|---|---|
| 基于 LangGraph Checkpointer 实现状态持久化 | 基于 LangGraph Checkpointer 实现状态持久化，**模拟网络中断后断点恢复成功率 100%**（8 次注入，0 次重复计算） | 有结果才是工程；⚠️ 括号里的数字要你自己跑一遍确认再写 |
| Redis 缓存 24 小时过期 | Redis 缓存 + **TTL ±10% 抖动防雪崩 + 进程内 LRU 降级 + single-flight 合并并发计算** | 从"用了什么"变成"防住了什么" |
| 用户上传数据 → 识别角色 → 零代码适配 | 对任意 CSV 做**动态 Schema 推断**（按列 dtype / 取值分布识别表达矩阵、分组表、注释表），支持 3 类表 × N 种列名写法 | 具体可验证，比"零代码"可信 |
| 基于 create_react_agent 实现多工具 Agent | **手写 ReAct 循环**（状态 / 模型 / agent / tools / 条件边 5 个零件）+ **四道护栏**（步数预算 / 指纹去重 / 单工具超时 / recursion_limit 对齐） | 现成组件不做去重和超时；"手写"才解释得清每一行为什么在 |

> 关于"断点恢复 100%"这条：`InMemorySaver` 重启进程必丢；只有 `USE_POSTGRES=true` 下才成立。**写之前先跑一次进程重启验证**，否则面试官让我现场演示就露馅。
